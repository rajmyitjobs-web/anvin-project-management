1. Start here: the daily operating cycle

My Project Management v36 | User manual, process flow and dashboard/report data guide | 22 November 2026 | Qatar time.

The application follows Customer > Project > Companies > Modules > Activities > Daily allocations > Actual hours > Timesheets and reports. The daily activity entry uses one Activity Date and Hours. One man-day is 8 hours; a half-day session equivalent is 4 hours. Enter net decimal hours: 1.5 means 1 hour 30 minutes, not 1 hour 50 minutes.

For a first setup, the workspace owner completes masters, users and permissions before the project manager creates projects. Each morning, the manager reviews pending work and allocates the day. Each consultant reports actual hours and remarks. The manager reviews client deductions, follow-ups and reports.

This manual describes the IIS / SQL Server edition. Hosted preview or browser-local demo data is separate from your live company database. Sign in at the company IIS address to work on shared company records.

3. Roles, login and permissions

Use your company email/password login. A team profile and a sign-in account are related but different: adding a name to Team management does not itself prove that a usable login has been created. Use User master / SQL Server & accounts as available to the workspace owner to create or manage company accounts.

Workspace owners control role configuration. Role master defines roles such as Project manager, Project lead and Consultant; Role permissions defines their allowed actions. Custom roles can inherit a base role. The actual permission matrix is authoritative; a job title or being named Project Manager does not grant every permission automatically.

Project assignment gives scope/visibility. Project manager, in-charge, module membership and task participation can give project access, but task and actual-entry visibility still follow the account permissions. An employee with partial access can see incomplete project totals. Use an authorized account with full project visibility for a complete client report.

5. Create and expand a project

Open Projects > create a new project. Choose the customer and stage/type; enter the project code, name, contact, industry, Project Manager and Project In-charge. Review start and target go-live dates. New-entry date fields default to today and are editable.

Select module checkboxes. Each selected module needs a primary in-charge; tick additional people where several consultants will work on it. Project-level module assignments are defaults, not automatic daily tasks.

Enter Number of companies (normally 1 to 100) and real company names. Saving creates company records with the selected module defaults. Company names must be unique within the project. Review each company card afterwards.

To expand later, open the project and choose Edit project / modules / company count. Increase the company count and/or check additional modules at any project stage. Existing modules remain selected. Count cannot be reduced below existing company records, to protect their plans and history.

The default option adds newly selected modules to existing companies without replacing consultant overrides. A live company receiving a new module becomes Not ready for the additional scope; existing actual go-live dates and module history are retained. New companies inherit current project defaults. The separate matching-default option is opt-in for owner changes.

Changing project defaults does not reallocate existing daily work. Edit the allocation itself when a different employee must perform a task. Company-specific names, consultants and go-live fields are maintained through Edit / go-live on the company card.

6. Plan companies, activities and budgets

Within a project, review each company and its modules. Use Add activity to build a dated baseline, or apply an implementation template and then review every generated activity, consultant and date. Baseline start/finish dates remain useful in Project plan even though Daily Allocation uses one activity date.

An activity has one primary task owner and may contain multiple daily allocations to different employees. Do not confuse task ownership with the person on each allocation. Baseline effort is stored in half-day session equivalents: planned hours / 4 for new hours-only tasks.

Use the project client implementation budget to enter contracted man-days and classify any legacy session hours. Budget hours = contracted man-days x 8. A project with no budget shows Not set; setting a budget does not create or approve work.

Keep company/module go-live status and actual dates under review. A project is treated as completed only when it has activities, task-count progress is 100%, and all configured companies are marked Live. A report does not itself change go-live status.

7. Allocate daily work: one date and hours

Open Daily allocations and choose Create task & allocate. Select project, company, module and activity. The type comes from the project for new work. Optionally select a matching existing planned activity instead of creating another task.

Enter Activity Date and Planned Hours. Choose onsite/offsite, client/internal and one or more employees. Add clear instructions and save. Each employee receives an allocation. For a shared session, planned hours apply to each selected employee.

Hours must be above 0 and at most 24 per allocation. Enter net hours excluding breaks. No start/end clock time is required. A new task derives its baseline start/finish from this one activity date; existing task baselines are preserved.

To change pending work, use Edit allocation. Rescheduling rights are required to change date or planned hours. Once work is reported, retain the original allocation date and add another allocation for a later visit. Editing an allocation does not move another employee allocation automatically.

Daily cards and the work table use allocation date, which may differ from actual work date. A changed actual work date will therefore appear in a different timesheet period without moving the original planned allocation.

8. Weekly visits, calendar and WhatsApp

Use Weekly visit worksheet to select employee, customer, project, matching activity, optional planned task, date, times, onsite/offsite and notes. The weekly worksheet retains clock scheduling; the simplified daily form does not require it. Saving the worksheet creates the canonical daily allocations.

New weekly rows default to today when today is in the selected week; choosing another week uses that week. Review the selected week before saving. Daily allocations are the place to complete remaining instructions and actual reporting.

Hours-only daily allocations appear as date-based calendar entries and export as all-day ICS events with the hours in the title. They do not reserve a clock-time slot. Existing timed visits and meetings keep their original scheduled times. Use the calendar and weekly plan to review dates; use Daily allocations to edit allocation records.

Use the WhatsApp action on an individual allocation to prepare a message and employee link. Review and send it yourself in WhatsApp. The team report can be downloaded/copied and attached to a group. The application does not silently send WhatsApp messages.

The link must use an IIS address reachable by the consultant. localhost works only on the computer hosting IIS. Sharing a link does not create an account or grant access. The employee must use their company login and have the correct role/project access.

9. Report actual activity

Open Daily allocations, Team/My dashboard, or a timesheet row and choose Update actual. The simplified form has Activity Date, Actual Hours, Status, Completion %, Outcome/remarks and client-deduction choice. An AMC onsite activity may also show a visit checkbox.

When no actual report exists, planned hours are loaded for review. Saved actual hours and date take priority when reopening. Opening or cancelling the form never records hours. Review the date/hours, enter what was actually delivered and save.

Enter 0 for a status-only update. Completed work requires positive actual hours and an outcome. Future actual work is blocked. More sessions, awaiting confirmation and open updates require a clear follow-up note. Use another daily allocation to schedule the next confirmed visit.

For a team session, each employee must choose whether their own client-tagged hours deduct from the client. Internal work never deducts from the client. All positive employee hours still appear in timesheets, regardless of deduction. An authorized manager can correct actuals or deductions; audit history records the updater.

Task-level actual start/finish dates are derived from recorded work dates. If one employee completes a shared activity while other allocations remain incomplete, the activity can remain In progress. Allocation status and overall activity status are intentionally distinct.

Old clock/session entries remain readable. Direct numeric hours take priority when an entry is saved in the new form; an explicit numeric zero overrides old clock values. Existing timing fields are not used to invent another visit or duplicate actual hours.

11. Worked example: two consultants, one session

Finance training is allocated to Aisha and Daniel for 4 hours each. They both report 3 actual hours. Aisha selects Yes for client deduction; Daniel selects No. Both entries are Client-tagged.

Timesheets show Aisha 3 + Daniel 3 = 6 employee hours. Client deduction is 3 hours, not 6. Client non-deducted hours are 3. An 80-hour client budget has 77 hours remaining. Client man-days consumed are 3 / 8 = 0.375 (displayed with report rounding).

If the same shared onsite visit qualifies for an AMC contract and both required people attend, visit hours are counted once using the maximum attendee hours: 3 hours, not 6. If the contract requires 4 hours per visit, this visit is short even though employee timesheets total 6 hours.

Planned hours, employee actual hours, client deduction and AMC visit hours answer different questions. Do not expect them to be equal.

12. Where application data is stored and loaded from

In the live SQL edition, records are stored in the configured MyProjectManagement SQL Server database. The browser loads an authorized workspace snapshot through the application API, then renders dashboards and reports from those records. Refreshes are checked periodically (normally around 10 seconds in this build). A failed save is not evidence that SQL stored the change.

SQL reporting views read the same canonical JSON records; they are not separate manually maintained ledgers. In the browser preview/local mode, data lives in browser storage instead, so clearing/changing browsers can affect demo records. Use the live SQL edition for shared team data.

15. SQL reporting map for administrators

Use the application for ordinary editing. Direct SQL changes can bypass validation, relationships, audit and permissions; an administrator should take a backup and understand the JSON model before any repair. Never share SQL credentials with consultants.

The v31 numeric-hours reporting patch remains required in v36. New allocation JSON uses plannedHours and actualHours; numeric zero is authoritative. Older entries fall back to stored clock times/breaks, then legacy half-day units. SQL views preserve those rules. v36 adds documentation and does not require another schema change.

16. AMC process and alerts

For an AMC-stage project enter contract start/end, cycle (daily, alternate days, weekly, monthly, quarterly, six-monthly or yearly), visits per cycle, hours per visit and required staff. Review the suggested weekly visits before creating allocations.

Only onsite allocation evidence within the contract/cycle is used for compliance. A shared session is grouped by its AMC visit link or team group; independent hours-only allocations use their own visit keys. Per-visit credited hours use the maximum attendee hours, not the sum of employee timesheets.

Qualification requires the required people and sufficient per-visit hours. A short visit can contribute attended hours while still failing the qualifying-visit target. Closed-cycle visit/hour gaps create overdue alerts; future cycles should be reviewed for missing scheduling.

Employee timesheets and client deductions remain separate. Marking No for client deduction does not remove the employee hours, and does not automatically invalidate a legitimate onsite AMC visit. Offsite/internal support may still be employee work without being an onsite compliance visit.

18. Administration, backups and release control

Keep the application version, database patch history and a backup together. Verify the displayed version after an IIS update. Back up both SQL data and the deployed site before upgrading; retain appsettings configuration, web.config and the authentication key directory.

For v36, install the updated application and guide. There is no additional SQL schema change over v35. If upgrading from an earlier version, use the cumulative v36 upgrade to include the v31 numeric-hours reporting and v35 change-request prerequisites.

Preserve the existing IIS configuration and keys when replacing publish contents. Restart the application pool and hard-refresh the browser. Do not run a fresh-database setup script as a routine update. Complete rollback uses the paired application/database backup; old application versions may not understand direct-hour entries.

The full manual and process-flow PDFs/Word files in this release contain examples and operating instructions only, with no live company records or credentials. Users can open User manual & process flow in the application; the online and PDF/Word versions contain the same guide content.

20. Choose an enterprise theme

Open Appearance & Help > Appearance, or use the theme button in the top bar. Choose Midnight Blue, Light Workspace or Charcoal & Amber. The default is Midnight Blue. Each theme applies to navigation, dashboard panels, tables, forms and dialogs.

Midnight Blue uses a navy navigation rail and blue actions. Light Workspace uses a white sidebar and indigo controls. Charcoal & Amber uses a charcoal sidebar and amber actions. All three retain light data surfaces for readable forms and reports.

Choose Comfortable or Compact table spacing. Theme and spacing are saved only in this browser preferences. They do not change shared company data, employee permissions, saved actuals or report calculations. Another device can use another theme. Clearing browser storage resets the preference.

PDF/Word manuals and printed PSR reports keep their own document design. v36 also introduces a consolidated dashboard KPI ribbon, a project-register layout, sharper table and input borders, and local system fonts. No Google font download is required for the application theme.

21. Change requests: technical feasibility and revisions

Open Projects & Planning > Change requests. The workflow is Initiator draft > Project Manager feasibility review > CTO review > Technically feasible and ready to share with the client. Consultants, project leads and team leads can initiate requests when their configured role permits and they have project access.

Before first use the administrator runs the REQUIRED v35 SQL migration. It adds ChangeRequests and ChangeRequestDocuments tables and seeds missing CR permissions plus CTO and Team lead role templates. Create the actual CTO employee profile and company login, assign role rights, and confirm Project Manager in each project. The initiator, assigned PM and CTO must be different active people.

Create a draft with project, CTO approver, title, expected change, revision reason and numbered change points. PM comes from Project Master. Each non-empty line becomes P1, P2, etc. Save the draft, then upload its Word file and submit. A Word document is required for every submitted revision.

Word uploads support .docx and .doc up to 5 MB each. Uploads are retained, with the latest document designated for submission. Submitted documents cannot be replaced. The app gives a read-only .docx text preview with D1, D2 paragraph references; formatting, images and Word tracked changes are not reproduced. Legacy .doc files must be downloaded and opened in Word. Use original-file download for complete formatting. Text previews show at most 2000 non-empty paragraphs, with up to 5000 characters in each paragraph.

The assigned PM reviews the exact revision and chooses Approve, Amendment, Clarification or Meeting. Comments can refer to numbered points or D paragraph references. Amendment/clarification/meeting needs an explanation. A meeting request records a proposed date; confirm and create the actual appointment through Meetings. It does not silently book a calendar slot.

PM approval sends the revision to its assigned CTO. CTO has the same decision choices. CTO cannot approve before PM. Both approvals are required for Technically feasible. Use Awaiting my review to find your inbox; the register checks for updates around every 15 seconds while open, but does not replace a form while it is being edited.

Returned/meeting-requested revisions are read only. The initiator creates a new revision, explains the amendment, edits the points, uploads the revised Word file and submits again to PM. Client feedback after technical approval follows the same new-revision process. Approval is never copied to a new revision.

Technically feasible means this exact revision is ready to share, not that the client or commercial terms are approved. Download that approved revision Word file and send it through your normal process. The app does not send email or WhatsApp automatically, and its private document URLs are not public client links.

Revision history retains points, documents, reviewer decisions, point/paragraph comments, proposed meetings and audit timestamps. The register shows up to the latest 200 accessible requests. Filters show My requests, Awaiting my review or Ready for client. Company login, active role permissions and assignment are enforced by the server.

22. Change-request data, access and backup

CR records use dedicated SQL tables and authenticated /api/change-requests endpoints, separate from the ordinary workspace snapshot. The CR register counts current revision states. My requests uses initiator ID. Awaiting my review uses current Pending PM/CTO status plus assigned reviewer ID. Ready for client uses current Technically feasible state. Historical approved revisions remain available even if the latest revision is being amended.

Role permissions include Create/revise own change requests, Review as Project Manager, Approve as CTO and View all CRs within project scope. Initiators and assigned reviewers can read their request and revision history. Broad register visibility does not itself give authority to approve. Only the assigned reviewer at the current pending stage can decide.

Word bytes are stored in dbo.ChangeRequestDocuments.Content with file name, revision and SHA-256 hash. They are not written under wwwroot or a public upload folder. Every download/preview checks the active company login, workspace and CR access. CR metadata and files use no-store responses. Changes use a version check; a stale update returns a conflict instead of overwriting another decision.

Full SQL database backups include CR metadata, approval history and Word documents. The ordinary workspace JSON export/import does NOT include these dedicated CR tables or document bytes. Keep SQL backups and allow for attachment storage growth. There is no CR delete function in this version. If a project is removed, retain CR audit history; creating further revisions requires a valid project record.

23. Upload Activity Master and Project Plan from Excel

Activity Master: Masters & Setup > Activity master > Download Excel template / Upload Excel. Project Plan: Projects & Planning > Project plan > Download Excel template / Upload Excel. Import buttons follow existing master/plan permissions. In the company IIS edition they save to SQL Server; in the browser demo they save only to that browser.

Download the template from the appropriate screen. Fill the first worksheet below its heading row. In-app templates include reference sheets for available activity types or projects/companies/modules, activity codes and consultant IDs/names. Those reference sheets are not imported. Standalone blank templates are included in this release; in-app templates are better for matching your company records.

Activity Master columns: Activity Code, Activity Name, Activity Type, Description, Status. Code/name allow up to 140 characters; type must match an existing active type code or name. Status is Active or Inactive (default Active). Description is optional, maximum 1000 characters. Codes are unique across the catalog and names are unique within their type, including inactive records.

Project Plan columns: Plan Reference, Project Code, Company, Module, Activity Code, Consultant, Planned Start, Planned Finish, Planned Hours, Priority, Notes. Use an existing accessible project and exact company name. Company may be blank only when the project has one company. Module must be active and selected for that company; General is allowed. Activity code must be active and match the project stage. Consultant accepts exact ID, unique name or company email; using IDs avoids duplicate-name ambiguity.

Plan Reference is your unique import line code (up to 50 characters), unique within a project. Re-uploading the same references is rejected. Identical company/module/activity/consultant/date baselines are also rejected, even with another reference. Import is ADD ONLY: it never overwrites existing activities or actual work.

Plan dates accept yyyy-mm-dd text or normal Excel date values. Empty date cells default to today and show a preview note; date headers are still required. Finish must not be before start. Planned Hours are total baseline effort, above 0 and at most 4000. They become half-day session equivalents by dividing by 4. Priority is Low, Medium or High (default Medium). Notes are optional, up to 2000 characters.

Select Upload Excel, choose .xlsx or comma-separated UTF-8 CSV, then Preview file. The first sheet/header row 1 is used; maximum file size is 5 MB and maximum 500 data rows. Formulas, protected/encrypted formats and .xls/.xlsm are not supported: paste values and save as .xlsx. Keep codes/references as text to retain leading zeros. For old browsers unable to decompress .xlsx, use a current Chrome/Edge or save the first worksheet as CSV.

Preview shows normalized values, source row numbers, errors and warnings. No records are saved at preview. Import all rows is enabled only when every row is valid. Correct the original Excel file and preview again if errors appear. There is no partial-row import. A shared workspace version check rejects stale previews: reload/re-preview instead of overwriting another user changes.

Project Plan upload creates To do baseline tasks with dates, owner and effort. It does NOT create daily allocations, employee actuals, timesheets or go-live events. Schedule imported work from Daily allocations or the weekly worksheet. Uploaded activity master rows become selectable by type in later plans/allocations.

Activity import uses Manage Activity Master plus View All Projects permissions. Plan import uses Manage Plans within each project scope. Shared preview/commit runs server-side validation again before one database transaction. The file itself is read in the browser; row data is sent only to the company API and the source Excel file is not stored as an attachment. No new SQL tables/schema are required by v36. Existing v31/v35 prerequisites still apply.
